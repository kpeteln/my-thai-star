## Domain Descriptions

### 🧑 User Management

Handles authentication, authorisation, and user preferences.

| Entity | Purpose |
|---|---|
| `user_role` | Three built-in roles: **Customer** (0), **Waiter** (1), **Manager** (2) |
| `"user"` | Registered users with BCrypt passwords and optional TOTP 2FA |
| `user_favourite` | Many-to-many relationship allowing users to bookmark dishes |

### 🍜 Dish Management

The restaurant menu catalogue.

| Entity | Purpose |
|---|---|
| `image` | BYTEA binary store for dish cover photos |
| `category` | Taxonomy tags (Thai, Vegetarian, Vegan, Curry, …) with display order |
| `ingredient` | Available extra ingredients/toppings with optional surcharge |
| `dish` | Core menu item with name, description, base price, and cover image |
| `dish_category` | M:N join: a dish can span multiple categories |
| `dish_ingredient` | M:N join: defines which extras are available per dish |

### 📅 Booking Management

Table reservation lifecycle.

| Entity | Purpose |
|---|---|
| `restaurant_table` | Physical tables with seating capacity (4, 6, or 8 seats) |
| `booking` | Reservation with token, date, booking type, and party size |
| `invited_guest` | Email-invited guests for group (type=1 GSR) bookings |

### 🛒 Order Management

Order placement and tracking.

| Entity | Purpose |
|---|---|
| `orders` | An order linked to a booking (host or guest) |
| `order_line` | One dish × quantity within an order, with optional note |
| `order_dish_extra_ingredient` | M:N: extra ingredients selected for a line item |

### 📊 Analytics & Machine Learning

Demand forecasting and geo-clustering.

| Entity | Purpose |
|---|---|
| `date_info` | Historical calendar + weather data (ML feature engineering) |
| `prediction_all_forecast` | Per-dish demand forecast output from ML service |
| `prediction_all_models` | Serialised ML model parameters (key-value) |
| `prediction_forecast_data` | Feature input set for forecasting (date, temp, holiday) |
| `addresses` | Geocoded user addresses for heatmap/clustering analytics |

### 🔧 Infrastructure

| Entity | Purpose |
|---|---|
| `binary_object` | General BLOB storage (devon4j BinaryObjectService) |
| `rev_info` | Hibernate Envers audit trail (one row per transaction) |

## Business Rules

| Rule ID | Description | Enforcement |
|---|---|---|
| **BR-001** | Host booking token format: `CB_YYYYMMDD_<MD5hex>` | `CHECK` constraint on `booking.booking_token` |
| **BR-002** | Guest booking token format: `GB_YYYYMMDD_<MD5hex>` | `CHECK` constraint on `invited_guest.guest_token` |
| **BR-003** | `expiration_date = booking_date − 1 hour` | Application layer (`BookingmanagementImpl.saveBooking`) + CHECK `expiration_date < booking_date` |
| **BR-004** | `assistants ∈ [1, 99]` | `CHECK` on `booking.assistants` (from `@Min(1)` + `@Digits(integer=2)`) |
| **BR-005** | `booking.canceled` defaults to `FALSE` | Column `DEFAULT FALSE` |
| **BR-006** | `user.two_factor_status` defaults to `FALSE` | Column `DEFAULT FALSE` |
| **BR-007** | `dish.price ≥ 0`, `ingredient.price ≥ 0` | `CHECK` constraints |
| **BR-008** | `order_line.amount ≥ 1` | `CHECK` constraint (from `@Min(1)`) |
| **BR-009** | `username` and `email` must be unique | `UNIQUE` constraints on `"user"` |
| **BR-010** | Each dish has exactly one image | `UNIQUE (id_image)` on `dish` (OneToOne enforcement) |
| **BR-011** | Cancellation only allowed before `booking_date − hoursLimit` | Application layer (`mythaistar.hourslimitcancellation` config property) |
| **BR-012** | `modification_counter` increments on every UPDATE | PostgreSQL trigger `trg_increment_modification_counter()` |

### Token Generation Algorithm (BR-001 / BR-002)

```
token = prefix + "_" + YYYYMMDD + "_" + MD5(email + YYYYMMDD + HHmmss)

Where:
  prefix = "CB" (host/Common Booking) | "GB" (Guest Booking)
  YYYYMMDD = current date at time of booking creation
  MD5 = 32-character lowercase hex string
```

Source: `BookingmanagementImpl.buildToken()` — Java `MessageDigest("MD5")` implementation.

## Views

### `daily_ordered_dishes`

Aggregates order line amounts per dish per day. Used by the ML prediction pipeline.

```sql
SELECT ol.id_dish, DATE(b.booking_date) AS booking_date, SUM(ol.amount) AS amount
FROM order_line ol
JOIN orders o    ON ol.id_order  = o.id
JOIN booking b   ON o.id_booking = b.id
GROUP BY ol.id_dish, DATE(b.booking_date);
```

### `geo_booking`

Spatial join of orders → users → geocoded addresses for clustering/heatmap analytics.

```sql
SELECT ol.id_dish, d.name AS dish_name, b.booking_date, a.geocode, ol.amount
FROM booking b
JOIN "user" u  ON u.id = b.id_user
JOIN addresses a ON u.id = a.id_user
JOIN orders o  ON o.id_booking = b.id
JOIN order_line ol ON o.id = ol.id_order
JOIN dish d    ON d.id = ol.id_dish;
```

## Circular Reference Resolution

The schema contains a bidirectional one-to-one link between `booking` and `orders`:

```
booking.id_order  ──────→  orders(id)
orders.id_booking ──────→  booking(id)
```

### Resolution Strategy

1. **Create `booking`** without the `fk_booking_order` foreign key
2. **Create `invited_guest`** (references `booking`)
3. **Create `orders`** (references `booking` and `invited_guest`)
4. **`ALTER TABLE booking`** — add `fk_booking_order DEFERRABLE INITIALLY DEFERRED`
5. **`ALTER TABLE invited_guest`** — add `fk_invited_guest_order DEFERRABLE INITIALLY DEFERRED`

The `DEFERRABLE INITIALLY DEFERRED` constraint is checked at transaction commit, not at statement level, allowing both sides of the circular reference to be set within the same transaction.

### Seed Data Insertion Order

```sql
-- 1. Insert bookings (id_order = NULL initially)
INSERT INTO booking (..., id_order, ...) VALUES (..., NULL, ...);

-- 2. Insert orders (references booking — safe, no circular check yet)
INSERT INTO orders (..., id_booking, ...) VALUES (..., <booking_id>, ...);

-- 3. Update booking to link the order (within the same deferred transaction)
UPDATE booking SET id_order = <order_id> WHERE id = <booking_id>;
-- Deferred FK is verified at COMMIT — both sides now valid
```
